### Added

- `query.findDescendantsOfEach(refsOrRecords, options)`: what `findDescendants` answers for each element given, one answer per input position in the input order, with the same `collect` and `omit` options applied under each element. A record given is used as given (its `children` are followed, it is not read again); the refs are read in one store `getMany`. A flat collect under elements that are not the document root then reads every subtree at once, one `getMany` per level: the sixteen scope records of the scenario fixture cost 5 store reads and 992 records, against 96 reads and 1,008 records for one `findDescendants` call per scope. A record under two elements given (nested scopes) is answered for both; an element given twice is answered at each position, each position after the first with its own shallow copy of a record, and from what that position gave (a record read before a later commit answers its own children, a ref the stored ones); a ref that names no element answers empty groups. A path collect, and a flat collect under the document root, read per element as before. Works on every store, staged operations included; also as `query.any.findDescendantsOfEach(refsOrRecords)`, which collects every descendant tag of each element as `query.any.findDescendants` does.
- `STORAGE_KINDS_VERSION` is 6: the shared `Query` shape gained `findDescendantsOfEach`, so a copy of the library at another version finds no storage kind registered by this one (`PROJECT_STORAGE_NOT_REGISTERED`) instead of a store whose query it cannot call. Version 5 was `getChildrenOfEach`'s.

### Changed

- `query.findDescendants` with a flat collect (a tag name or an array) under an element that is not the document root reads its subtree top-down, one store `getMany` per level, following only the children that can hold a collected tag, instead of reading every record of each collected tag and climbing each one's parent chain (which switched to a whole-document read past 128 reads). Content the definition does not list is followed: an element it does not know, xs:any content, a transparent element, and every branch when a collected tag is itself unknown to the definition. Same answers, except two: each tag's records now come in id order (before, in the store's order), and a descendant placed where the definition allows no such tag, under elements the definition knows, is no longer found there. The element itself is still answered when its own tag is collected. Under the document root and for a path collect, reads are unchanged. In dev perf counters such a call shows `core::store::getMany` calls only: no `get`, `getByTagName`, `count` or `getByDocumentId`. Scenario benches, 16 scope roots on the 8,189-record fixture: from 16 `count` + 16 `getByTagName` (8,192 records) + 7,696 `get` + 16 `getByDocumentId` (131,024 records) to 96 `getMany` moving 1,008 records; the new one-call scenario, given the scope records, takes 5 `getMany` and 992 records.
