### Changed

- The SQLite store answers `findByAttributes` from an attribute index instead of reading the whole tag. Each (tag, attribute) pair a lookup asks of a document is indexed in the project file the first time it is asked, in the background and in short slices, then kept exact by SQL triggers on every write. Until the pair is ready, its lookups are filtered inside SQLite, so only the matching records are read out. On a synthetic document of 60,000 records, looking up one uuid among 20,000 elements took 83 ms before and takes 0.1 ms once the pair is built. Only the pairs that are queried are indexed: the file grows with them (+12 % for two pairs covering a third of the records), and a write costs about twice as much for records of a tag with pairs, unchanged for the others. The file keeps its layout: a project written by this version still opens with an older one.
- `findByAttributes` with a long list of values checks each element against a set built once per call instead of searching the list for every element: a 5,000-value list over 5,000 elements no longer takes quadratic time.
- `ENGINE_WIRE_PROTOCOL` is 4 and `HUB_PROTOCOL_VERSION` 8: the engine serves the attribute lookup over its wire, so a page and an engine of different versions refuse each other instead of failing on the member.
