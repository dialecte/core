### Changed

- A transaction that looks one tag up by attribute values many times reads that tag once and answers the rest from memory. At the 8th `findByAttributes` of a tag in one transaction, the tag is read whole (one store call). Every later lookup of it, and every `getRecordsByTagName` of it, then makes no store call. The staged writes are laid on top as before, so the records and their order are those the store's lookup gives. The first seven lookups ask the store one each, as before: a transaction asking a tag a few times reads nothing more. A lookup the store's own attribute lookup does not take (a store without one, or a filter of only `xsi:type` or QName-typed values) reads the tag whole as before, and a `getRecordsByTagName` in a transaction does too: such a read now keeps the tag, so the transaction's later lookups and tag reads of it make no store call. In a document above 250,000 records the tag is read whole later, at `records / 2,000` lookups (the document's record count is read once per transaction). On a 59,000-record document over SQLite, one template apply went from about 19,600 store lookups (5.8 s) to one read of each tag it asks (about 160 ms).
- A transaction's cached reads follow changes told on the project channel: once another view's commit, an undo or a reimport of the document is told, the transaction's next read drops what it read before (its records by id included) and asks the store again. Before, the records a transaction had read stayed cached until it ended, so a record read before another view's commit was answered as it was.
- `STORAGE_KINDS_VERSION` is 15: the shared context shape gained the transaction's read cache, so a copy of the library at another version finds no storage kind registered by this one (`PROJECT_STORAGE_NOT_REGISTERED`).
