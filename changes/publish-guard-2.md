### Fixed

- The push to main never publishes a version at or below npm's latest: a lower or equal version (a downgrade, a typo such as `0.0.8` after `0.8.0`, a version that is not semver, `01.0.0` included) fails the publish run with the reason, and a version npm already has is never published again. A first publish (npm answers E404) publishes. The decision lives in `scripts/publish-guard/run-publish-decision.ts`, run by `_check-npm-version.yml`.
- A push that leaves the version unchanged decides from git alone and never asks npm, so an npm outage cannot fail it. On a version-changing push, a failed npm or git lookup fails the publish run with npm's or git's reason (`npm view --json`; only a success or an E404 counts as an answer), instead of being hidden and read as "npm does not have it".
- A pre-release version (one holding `-`) is published under the `next` dist-tag, never as `latest`, and only when it is above npm's `next` too, so `next` never moves back.
- A missing release tag is recovered: when npm has the version and its tag is missing, the version-changing push (a re-run of the release push, or a revert to a published version) pushes the tag on its own commit, without publishing. A release tag that exists while npm lacks the version fails the run with the reason, instead of failing after the publish.
- `_publish.yml` and `_tag-release.yml` are called by `publish.yml` only (no `workflow_dispatch`, which skipped the guard); `_publish.yml` passes the dist-tag to `npm publish` through the environment.
- `_check-npm-version.yml` says what a merge-queue batch does: its head is published, so the ruleset keeps the queue at one entry per merge.
