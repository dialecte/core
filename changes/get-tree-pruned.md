### Changed

- `query.getTree` reads level by level and decides for each child, from its tag alone, before reading it: the `select` keys at that level (auto-recursion and the `transparentElements` it sees through included), a tag-only `omit` and `depth`. A branch it cannot keep is never read; `where` and an `omit` with `where` are checked once the child is read, before its own children are. One `getRecords` per level, staged writes and the transaction cache answering first, so a bounded `depth` or a `select` inside a transaction with pending writes no longer reads the whole document. A ref without id reads its root by its tag name first. With no `select`, no tag-only `omit` and no `depth`, one whole-document read stays. Same trees. Scenario "getTree with a narrow select": 1 `getByDocumentId` moving 8,189 records → 1 `get` + 11 `getMany` moving 1,025 records (the tree kept). A child ref naming another tag than its record now raises `ELEMENT_TAGNAME_MISMATCH` on a pruned read, as every batch read does.
- Inside a transaction, a `getTree` of a singleton ref without an id that prunes (a `select`, a tag-only `omit` or a `depth`) now resolves the latest staged record of that tag, as `getRecord` does, instead of the first record of that tag in the whole-document read.
