# Dialecte (changing it)

Read the `dialecte` skill first: its layer model and reuse ladder apply here even more, because
in the repo you can see everything and are tempted to write a new primitive next to an old one.

Dialecte is treated as **greenfield**: internal and public APIs may change for clarity or speed.
When you see something that can be cleaner, faster or shared, do it in the same change rather than
leaving a note. A **breaking** change to public API or behaviour is always allowed as an option,
but it is proposed to the maintainer first (what breaks, why, alternatives) - never slipped in,
never avoided out of caution.

## The repos

Each package is its own git repo; work with them checked out side by side (one folder,
optionally `$DIALECTE_ROOT`).

| Repo                | Role                                          | Notes                                                                                     |
| ------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `core`              | schema-agnostic engine                        | no domain knowledge, ever; tests run on a dummy test schema                               |
| `scl`, `nsd`, `plc` | dialecte packages                             | `src/<version>/` = generated `definition/` + hand-written config, hooks, extensions, test |
| `create`            | XSD → definition generator + package template | Python XSD reader (via Pyodide) + TS derivation; `npm create @dialecte`                   |
| `cli`               | `dialecte` dev CLI                            | type coverage, type bench, narrowing, readability audit                                   |
| `playground`        | Vue/Monaco sandbox                            | run a script against a document; `DIALECTE_LOCAL=../x npm run dev`                        |

All of them are **npm** projects formatted with **oxfmt**, linted with **oxlint**, tested with
**vitest**: in core, in Node on the in-memory store, and in Playwright Chromium for the tests that
need a browser ([Test tiers](#test-tiers)). Never run pnpm or prettier inside them.

Inside a dialecte package (`src/<version>/`):

```
definition/*.generated.ts   DEFINITION, constants, types - generated by create, never hand-edited
config/                     dialecte config, namespaces, `namespace <Name>` hydrated types
constants/                  domain registries and literals repeated in several places
errors/                     defineErrors catalogue, import warning catalogue
helpers/                    pure record readers
hooks/<hook-name>/          one sub-file per concern, merged into that hook's result
hooks/shared/               logic shared by several hooks and by import
hooks/io/                   two-pass import session (collect, then resolve)
extensions/<ns>/{query,transaction}/<verb>.ts   business verbs, one per file
extensions/<ns>/public.ts   constants/guards/types offered to consumers
test/                       run<Name>TestCases, fixture validators
```

## Where does the change go? Decide and say it before coding

Walk it top-down, stop at the first yes:

1. **Does it already exist?** Run the reuse ladder from the `dialecte` skill across core AND the
   dialecte package (grep `extensions/*/{query,transaction}/index.ts`, `hooks/*`, `hooks/shared`,
   core `helpers/index.ts`, `utils/index.ts`). Test tooling and fixtures included.
2. **Must it happen on every write or import, whoever writes?** → a **hook** in the dialecte
   package (`hooks/<hook>/<concern>.ts`). Coherence (ids, names derived from references, cleanup of
   orphans) is a hook, not a verb the caller must remember.
3. **Is it a domain verb every consumer of this schema could use?** → an **extension** in the
   dialecte package (`extensions/<ns>/query|transaction/<verb>.ts`).
4. **Is it schema-agnostic engine behaviour** (traversal, mutation, IO, store, a missing hook
   point)? → **core**. Typed against the generic record model, tested on the dummy test schema.
5. **Only this app needs it?** → consumer code (custom extension in the app), not a dialecte change.

Two smells: a domain rule in core; a query whose only job is to feed a transaction (let the
transaction read the definition directly).

**Standard vs custom rule** (for a dialecte that implements a standard): the engine implements what
the standard says, and that is the default. A rule an expert wants that the standard does not
require is a consumer choice (an option on the verb or a policy hook, default = the standard). A
rule that contradicts the standard stays out of the engine (consumer override).

## Reading the standard

For a dialecte that implements a standard: the standard your dialecte implements is the truth its rules come
from, and a long text read once by one model is not a reliable source.

- **Markdown first.** Read the standard as markdown, citing `file:line`; never the PDF. A document not yet in
  markdown is converted first: markitdown for PDF, DOCX or PPTX; docling or pymupdf4llm when its tables come
  out broken.
- **The converted text stays private**: kept next to the plans, outside every package repository; never
  committed, never quoted or cited in committed text (code, doc, CHANGELOG, skill) or on GitHub. Committed text
  states the behaviour.
- **A confirmation** (a name, a type, a cardinality the code already follows): one reader, with line references.
- **A decision that changes what the engine does or accepts** gets the cross-check, once per decision:
  1. Two or three independent readers on the `standard` tier (at least one on another model or vendor when
     one is available): the same question, no shared notes, a `file:line` for every claim.
  2. One reader takes the whole relevant part, the others split it by section, so coverage does not rest on
     one model's retrieval.
  3. An adjudicator on the `strong` tier compares the answers: an agreed claim with matching lines passes; a
     disagreement, or a claim without a line, becomes a question for the user or the domain expert. Runs of
     one model share its biases, so agreement is evidence, not proof.
  4. The result (question, claims, lines, verdict) goes in the plan's research folder, next to the plan: later
     lots reuse it instead of reading the standard again.

The tiers are those of the `dialecte-lot` skill (its model-tiers reference).

## The workflow

1. **Orient**: read the nearest existing example of what you build (an extension in the same
   package, a hook sub-file, its test) and the package's `doc/` page for the surface. Copy shapes,
   don't invent them. A new extension verb starts from `npx dialecte new verb <namespace>
   <query|transaction> <name>`: it writes the function, its `.types.ts`, a red table case marked
   `only`, the barrel export and the namespace registration, and lists the `FILL:` placeholders
   (`skills check` refuses them until written).
2. **Red first, proven by the cli**: the tests come first, from the spec, before any production code:
   a test written after the code can be shaped to please it. Write the table cases (the `dialecte`
   skill's references/testing.md); where the code does not exist yet, a stub with its real type whose body
   throws `new Error('not implemented: <name>')`, called inside an `expect(...)` a matcher completes.
   Remove every focus marker (`.only`, `only: true`) **before** the red: `tdd red` refuses a file holding
   one, and removing it after would be an edit after red. Then `npx dialecte tdd red`: each new or changed
   case must fail on an assertion (or the stub's error inside `expect`); a pass, a missing export, a type
   or syntax error, a timeout is refused with its kind - fix the test. Then the minimum code, the test code
   untouched (tests, helpers, fixtures, snapshots), until `npx dialecte tdd green` (test code edited after
   its red is refused there; snapshots are never written by the run: write a snapshot test's snapshot
   before the red). `npx dialecte tdd status` shows where each case stands. With sub-agents, the test, the
   test review and the code are three agents (`dialecte-lot`, Station 1). Tests share a loaded machine: a
   test owns its temporary folder, and a time bound carries slack and never counts a worker's start; a test
   that reads the disk, spawns a process or measures time carries an explicit bound, named
   (`SOURCE_SCAN_TIMEOUT_MS` in core's `src/test/test-timing.constants.ts`) and several times what the test
   takes on a quiet machine; the test review and the review check that every such test has one. A suite that
   spawns git clears the inherited `GIT_*` variables before any test (a setup file in the `setupFiles` of
   every vitest project that runs the suite - read the config, add one when none does it), for the code
   under test as much as for its own calls: under a commit hook in a worktree they point at the outer repository
   ([references/traps.md](references/traps.md), Tests).
3. **Implement under the code rules**: [references/code-rules.md](references/code-rules.md).
   Read it before writing the first line; most review comments come from it. `npx dialecte rules`
   checks them on the changed files.
4. **Gates** (below), then docs + CHANGELOG if the surface changed.
5. **Independent review**: have a fresh reviewer (a sub-agent with only the spec, the diff and
   these rules, or a human) read the diff against the previous version before hand-over. Self-review
   re-reads your own intent and misses weakened assertions and unusable types.
6. **Hand over** through `npx dialecte handover <lots.json>`: the agent writes only the lots file, the
   command writes the hand-over folder and prints the card the user gets
   ([references/landing-changes.md](references/landing-changes.md)). The agent never commits or pushes.

## Test tiers

In a package whose vitest config has a `node` project (core), a test runs in one of two tiers.

- **Node by default.** Every test file runs in the `node` project, on the in-memory store, unless it is
  declared browser-only. Iterate with `npx vitest run --project node <path>`. The files of
  `NODE_STORE_CONTRACT_TEST_FILES` (the store contract, the IndexedDB-specific tests) run in the
  `node-indexeddb` project instead, on fake-indexeddb: `npx vitest run --project node-indexeddb <path>`.
  A new IndexedDB-specific test goes in that list AND in `BROWSER_ONLY_TEST_FILES` (real IndexedDB
  once per lot).
- **Browser only for a browser API** (`navigator.storage`, OPFS, a worker, real IndexedDB, the page's
  `DOMParser`, the save dialog or a download link): add the file to `BROWSER_ONLY_TEST_FILES` in
  `vitest.config.constants.ts`, `{ path, why }`, the `why` naming that API. Iterate with
  `npx vitest run --project browser <path>`. A file that reads the package from disk or starts node goes
  to `NODE_ONLY_TEST_FILES` the same way. The config refuses a listed path that names no file.
- **A difference between the tiers is a bug**, of the store or of the assertion. Never move a test to
  the browser list to hide it, never retry it beyond the one serial rerun every failing run gets (a case that
  fails in one tier only after that rerun is a difference, not a flake). Reproduce it with `--project node`, pin it with a red
  case first: in the store contract (`src/store/contract`) when a store answers differently, beside
  core's assertion helper (`src/test/assert-xml`) when it reads the XML differently between tiers.
  Then fix it. When the test's own assertion depends on something no store promises (an XPath `[1]`
  relying on an order the contract leaves open), fix that assertion in the test instead, with the
  reason in a comment. Then run the file in both tiers (`--project node` and `--project browser-all`).
- **No test names its store**: the runner's `useTestStorage` chooses (the `node` project's setup file
  sets the in-memory store, the browser keeps the local one). See the `dialecte` skill's
  references/testing.md for the assertions: XML text, XPath for small output, record expectations for
  big files.

## Definition of Done - every change, in the changed package

Run it with `npx dialecte gate --fast` while iterating and `npx dialecte gate --full` once per lot,
from the package root; before the branch merges, also the whole suite in the browser (step 4
below). The gate runs each step below unfiltered and judges it on its exit code and on the counts
the step printed (a test step that counts no test fails), prints one line per step,
restores the generated docs the package declares after the docs build, and refuses to run while a
hand-over script holds the repository. With `--fast`, a change that touches no test (a doc edit)
passes the tests step with the note "no test file is affected by the change"; any other run that
counts no test fails. Paste its lines in your report: they are the real counts. A gate of the same
mode on a tree it already passed, with the same lock, linked dependencies and steps, runs its hygiene and `tdd`
step, then answers the rest from that record (`reused`, from cli 0.2.0). `--no-reuse` forces a run: only when the
person asks, or when something outside the key changed (an edit, a lock or a linked dependency already makes a
new key).

Both modes run a **`tdd` step** after the hygiene: every new or changed test case holds a red receipt and a
later green one (`dialecte tdd red` / `green`), and the test code (helpers, fixtures, snapshots included)
is as the last red run froze it; a lot that changes no behaviour (wording, rename, docs) is declared
exempt by the orchestrator in `.dialecte/lot.json` (`{ "tdd": "exempt: <reason>" }`, never committed),
and the gate prints how many production and test files the change still touches.

`--fast` starts with the worktree's **hygiene**: nothing staged, no stash entry pushed on this
worktree's branch since `dialecte worktree add` made it (other branches' entries are only noted), and
every new file declared (`--declare <path>`, one per new file or folder; an undeclared one is a
warning). A failure names what changed and the read-only commands
to look at it.

**Test runs use the runner's defaults**: full parallelism, no `nice`, no `--maxWorkers`, no
`--no-file-parallelism`, no lock and no waiting on other sessions' runs or on the load - the machine is shared,
and that is the user's to manage: when they ask you to limit (to leave room for other sessions), do it for the
time they say. A run that fails is rerun **once, serially, on its failing files**: the same command, its
`--project` flags kept so the rerun stays in the failing tier, with the failing files and `--no-file-parallelism`
added (through an npm script, after `--`). Failing there too, it is a real failure; passing there, it is **flaky in
parallel** - a defect of the test or the code, reported with its files and fixed at its cause (a wall-clock bound
tuned on a quiet machine, a shared temporary folder, port or build output, browser state, an inherited environment
variable), never answered by throttling the next runs. The gate does this rerun itself on a vitest test step: a
step that passes on it is green and its line says `flaky in parallel` with one `flaky <file>` line per file - read
the flag on a green gate; one that fails again says `real failure`. A failing step line that says neither comes
from a cli without the rerun: rerun its files by hand. Such a cli may still hold a machine lock around `--full`,
its heavy steps and `tdd`: let it wait.

**Waiting on a long run** (`gate --full`, a mutation run, a bench): start it in the background with its output in
a log - your harness's background run, or `cmd > "$log" 2>&1 & echo $! > "$pidfile"` - then wait for the
harness's completion notice or on that PID (`while kill -0 "$(cat "$pidfile")" 2>/dev/null; do sleep 5; done`),
with an upper bound tied to the run's expected duration; at the bound, report "timed out" with the log's tail.
Never wait with `pgrep -f "<text>"` when that text is in your own wait command: the loop finds itself and never
ends (`pgrep -f "[v]itest run"` if it is unavoidable). When the wait ends, read the exit code and the log's
summary line: "no process found" is not a pass.

Read the step list in the package's `package.json` (`"dialecte": { "gate" }`) when it overrides the
defaults. The gate, `rules`, `new verb`, `handover` and the `skills` check of step 6 come with `@dialecte/cli`
0.2.0 or later. Read the package's pin first (`npm ls @dialecte/cli`): with an older one, every such command
runs as `npx @dialecte/cli@^0.2.0 <command>` - never `@latest`, which can be older than 0.2.0 and lacks them -
or the steps by hand:

1. `npm run check` - type-checks sources AND tests, lint, format. Never a bare `tsc --noEmit`
   (`tsconfig.json` is a solution file and checks nothing).
2. `npx oxfmt <changed files>`.
3. `npm run build` - runs the type-check in parallel and emits declarations (vite-plugin-dts),
   which catches union-assignability errors the editor misses.
4. The tests, by tier: `npm run test:node` per step (the fast gate runs its changed files), the
   browser-only list once per lot (`npx vitest run --project browser`, in the full gate), and
   `npm run test:browser:all` - the whole suite in the browser - once before the branch merges. A failing run of
   any tier first gets its one serial rerun (above); a case that still fails there while it passes in the other
   tier is a tier difference - a bug, never retried further, never hidden ([Test tiers](#test-tiers)). A package without a `node` project: `npx vitest run`
   (`npm run test` is watch mode in some packages; create uses `npm run test:ts` + `test:py`).
   One file while iterating: [Test tiers](#test-tiers).
5. `npm run doc:build` - the VitePress docs build.
6. `npm run skills:generate`, then `npm run skills:check` - every change, not only one that touches a skill:
   the check fails on a name, path or script a skill cites that no longer exists, and on a public function
   without its JSDoc summary and `@intent` (below). The scripts run the package's pinned cli; with a pin
   older than 0.2.0 they check neither, so run `npx @dialecte/cli@^0.2.0 skills generate` and
   `npx @dialecte/cli@^0.2.0 skills check` instead (it fails loudly while 0.2.0 is unpublished, never falls
   back to an older cli).

If public API or user-visible behaviour changed, it is not done until you also:

- give every new public function or method a JSDoc whose first paragraph says what a caller gets, and an
  `@intent` tag - comma-separated phrases naming what a caller is trying to do when they reach for it
  (`@intent validate an exported file against its XSD, find what a document breaks`) - even when the
  functions beside it carry none. Public means any function exported from an entry of the package's
  `package.json` `exports` (every entry: the main one, `./utils`, `./helpers`, `./sqlite`, `./test` - other
  packages' suites import the test entry - a dialecte's version entry) and any method reached from `project`,
  `doc`, `doc.query` or `tx`. The skills' API index (`skills/dialecte/references/api.md`, `api.json`, what
  `dialecte api find` answers from) is built from these two: a function without them is one the next agent
  cannot find, and writes again. An export not meant for callers is tagged `@internal` instead and stays out
  of the index;
- update the `doc/` page that describes that surface (types, verbs, contracts),
- add a line under `## UNRELEASED` in the package's `CHANGELOG.md`, written for the user, and
- update the package's `skills/` when the change touches what a skill describes (API, hooks,
  extensions, scripts, layout, rules); `npm run skills:generate` refreshes the generated tables, and the
  check runs in the gate (step 6).

Type performance: `npm run type-bench:check` compares type instantiations with
`benchmarks/types/baseline.json` (one per version folder in a dialecte package:
`benchmarks/types/<version>/baseline.json`; 5 % gate). A breach is a **think point**, not a wall: measure
and explain the growth; if it is legitimate, re-baseline with `npm run type-bench` in its own lot.
Never hand-edit `baseline.json`, never twist code to dodge the gate.

Run slow gates (create's `npm run proof`, corpora) once per lot before hand-over, not after every fix.
Fast targeted runs while iterating. Mutation testing runs beside the lot instead (below).

## Mutation testing

In a package that declares a mutation scope (`package.json` `"dialecte": { "mutation" }`), `dialecte mutants`
(`@dialecte/cli` 0.2.0) runs StrykerJS on it and keeps every survivor in a ledger until it is handled; `dialecte
mutants` with no verb prints each verb's usage. The scripts do the bookkeeping, so your tokens go to judgment only.

- **The switch is per lot**, in `.dialecte/lot.json`: `dialecte lot mutation off|changed|audit|gate`. Without it, a
  lot whose diff touches the scope runs `changed` (its changed lines), any other lot `off`. `gate` is for a
  robustness lot only: its hand-over waits for a run reported on the tree it commits, so it runs again after the
  last fix. `audit` mutates the whole scope.
- **Off the critical path.** Start `dialecte mutants run` as a background run of your harness (the cli has no
  background flag): the run is written `running` in the store before Stryker starts, so a killed session leaves a
  `died` run, never nothing. Go on working (to wait on it: Waiting on a long run, above). A hand-over does not wait
  for it, except a `gate` lot's; a merge does.
- **Before every hand-over and every merge: `dialecte mutants status`.** Pending items block the card and the
  `handover run` guard: `new` survivors of the package (whatever their lot), `died` runs, and a `running` run of the
  branch for a merge or a `gate` lot (on a plain hand-over it is a `!`). `scheduled` survivors belong to their
  follow-up lot and do not block.
- **Judge one file at a time**: `dialecte mutants judge [--file <file>] --json` gives each file's packet (code,
  covering tests, a family guess). Per survivor, one of:
  - a test that kills it (a `gap`: red first like any test), then run again;
  - `dialecte mutants record --key <key> --family <family> --reason "<why>"`, the reason saying in 200 characters at
    most why no tested behaviour changes. An `invariant-guard` or `fallback-never-taken` also gets a follow-up lot
    that deletes the guard or tightens the type: `dialecte mutants schedule <follow-up lot> <key>` first, then
    `record ... --removable` (a scheduled survivor keeps its follow-up when recorded; a recorded one can no longer be
    scheduled);
  - `dialecte mutants schedule <follow-up lot> <key>` when another lot owns it.

  The families are a closed list, the words of the judgment: `invariant-guard` (a check the types, or internal
  callers only, already guarantee), `fallback-never-taken` (a default no input reaches), `exhaustive-default` (the
  default of a switch that covers every case), `no-op-on-empty` (a skip of work that would do nothing),
  `perf-shortcut` (a cache or an early exit that only saves time), `static-init` (module-level setup),
  `schema-default-read` (a read of a value the schema already defaults), `wording` (message or log text). None
  fits: it is a `gap`. Judge on the standard tier; the strong tier only for a `gap` with no obvious test.

- **The cli is the only writer** of `.dialecte/mutation-records.json` and of the store under
  `<git-common-dir>/dialecte-mutation/`: never edit either by hand (nor anything else under `.git`).
- **Runs**: a `died` run is rerun, or `dialecte mutants abandon <run id>`; `dialecte mutants drop <run id>` removes
  only an abandoned run or a reported one the ledger took in.
- **Full audit** (`dialecte mutants run --mode audit`): before a release or on request, in the background; its
  survivors are scheduled as named follow-up lots, not fixed in the release.

A lot that builds tooling with shared state or drives an external tool has its own traps (plan it as a transition
table, one real run in a scratch clone, cited third-party values): [references/traps.md](references/traps.md), Tools
with shared state.

## Cross-package changes

A dialecte package depends on a **published** core version (an installed copy, not a symlink). A
core change is invisible to the package until you: build core → put its build where the package
resolves it (`npm install ../core` in the package, a symlink
`<package>/node_modules/@dialecte/core -> ../../../core`, or a copied `dist/`) → delete the package's
`node_modules/.vite` (vitest pre-bundles deps and keeps the old core). Before committing, the
package must depend on a released core version again; never commit the link. Release order: core
first, then the packages that pin it, each with its own bump lot.

## Verification traps (false greens)

Read [references/traps.md](references/traps.md) before trusting any gate output. The short list:
solution tsconfig checks nothing; tests have their own tsconfig; stale `.vite` cache after a core
swap; output-compacting shell wrappers can turn a failing gate into "ok" (run verdict gates raw and
read the counts); a doc build can rewrite a generated data file (restore it before the hand-over
script is written); before `@dialecte/cli` 0.2.0, `dialecte bench --help` runs the
bench and writes the baseline; a test that passes on its first run may be green by accident.

## Skills ship with the code

Each package carries the skills that describe it in `skills/<name>/` (published in its npm tarball):
core has `dialecte`, `dialecte-contributing` and `dialecte-lot`, create `dialecte-create`, and every dialecte
package its own `dialecte-<id>` with the knowledge of its schema. A skill changes in the same PR as the code it describes - never
in another repository afterwards. `@dialecte/cli` maintains them:

| Command                    | Does                                                                                                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dialecte skills sync`     | installs the skills of the app's dependencies into `.claude/skills` + `.agents/skills` (`--agent claude,copilot,agents`, `--copy`); `--from <workspace>` takes them from local checkouts                                                                         |
| `dialecte skills generate` | rewrites the `<!-- dialecte-skills:generated ... -->` blocks (verb map, method and export index, hook files) from the source                                                                                                                                     |
| `dialecte skills check`    | frontmatter, links, and every API / path / npm script a page cites must exist; generated blocks must be fresh; every public function and method has a JSDoc summary and an `@intent`; `--workspace <dir>` also verifies pages that describe several repositories |

Write claims so the check can verify them: API as `query.<method>` / `tx.<ns>.<verb>`, paths
relative to a package, scripts as `npm run <script>`. A deliberate mention of something outside the package goes in
`<!-- dialecte-skills ignore: token -->`.

## Performance work

Measure, don't guess: [references/perf.md](references/perf.md) (perf helper, node bench harness,
browser timeline, CPU profile). Classic regressions to avoid in review: per-element ancestor walks,
per-element queries without a cache, re-reading the same records in several passes, store reads
during import (import is in-memory two-pass by design, see the hooks rules in the `dialecte` skill).

## Never

- Edit a `*.generated.ts` file (regenerate with `dialecte-create`).
- Add a domain rule to core because it was convenient.
- Restate a registry or the definition by hand (see code-rules).
- Commit, push, or touch a repo's git index while a hand-over script may be running.
- Leave a known improvement as a "note for later" without doing it or explaining why you cannot.

## Retro gate - before you hand over

List in your hand-over every place where this skill was wrong, missing or misleading for the task,
and every correction the user made that a skill should have prevented. Then:

- **Inside a dialecte repository**: draft each skill edit as before/after and show it to the user; an
  approved edit goes in the same change (skills ship with the package that owns the code), through
  `anthropic-skills:skill-creator` loaded with the Skill tool - the eval case first, failing on the text
  before the change, as `dialecte-lot` describes - then `npm run skills:generate` and `npm run skills:check`.
- **In an app**: draft an issue for the package that ships the skill - the statement that was wrong
