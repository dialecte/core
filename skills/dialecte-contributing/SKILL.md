# Dialecte (changing it)

Read the `dialecte` skill first: its layer model and reuse ladder apply here even more, because
in the repo you can see everything and are tempted to write a new primitive next to an old one.

Dialecte is treated as **greenfield**: internal and public APIs may change for clarity or speed.
When you see something that can be cleaner, faster or shared, do it in the same change rather than
leaving a note. A **breaking** change to public API or behaviour is always allowed as an option,
but it is proposed to the maintainer first (what breaks, why, alternatives) - never slipped in,
never avoided out of caution.

## The repos

Each package is its own git repo; work with them checked out side by side (one folder,
optionally `$DIALECTE_ROOT`).

| Repo                | Role                                          | Notes                                                                                     |
| ------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `core`              | schema-agnostic engine                        | no domain knowledge, ever; tests run on a dummy test schema                               |
| `scl`, `nsd`, `plc` | dialecte packages                             | `src/<version>/` = generated `definition/` + hand-written config, hooks, extensions, test |
| `create`            | XSD → definition generator + package template | Python XSD reader (via Pyodide) + TS derivation; `npm create @dialecte`                   |
| `cli`               | `dialecte` dev CLI                            | type coverage, type bench, narrowing, readability audit                                   |
| `playground`        | Vue/Monaco sandbox                            | run a script against a document; `DIALECTE_LOCAL=../x npm run dev`                        |

All of them are **npm** projects formatted with **oxfmt**, linted with **oxlint**, tested with
**vitest in a real browser** (Playwright Chromium). Never run pnpm or prettier inside them.

Inside a dialecte package (`src/<version>/`):

```
definition/*.generated.ts   DEFINITION, constants, types - generated by create, never hand-edited
config/                     dialecte config, namespaces, `namespace <Name>` hydrated types
constants/                  domain registries and literals repeated in several places
errors/                     defineErrors catalogue, import warning catalogue
helpers/                    pure record readers
hooks/<hook-name>/          one sub-file per concern, merged into that hook's result
hooks/shared/               logic shared by several hooks and by import
hooks/io/                   two-pass import session (collect, then resolve)
extensions/<ns>/{query,transaction}/<verb>.ts   business verbs, one per file
extensions/<ns>/public.ts   constants/guards/types offered to consumers
test/                       run<Name>TestCases, fixture validators
```

## Where does the change go? Decide and say it before coding

Walk it top-down, stop at the first yes:

1. **Does it already exist?** Run the reuse ladder from the `dialecte` skill across core AND the
   dialecte package (grep `extensions/*/{query,transaction}/index.ts`, `hooks/*`, `hooks/shared`,
   core `helpers/index.ts`, `utils/index.ts`). Test tooling and fixtures included.
2. **Must it happen on every write or import, whoever writes?** → a **hook** in the dialecte
   package (`hooks/<hook>/<concern>.ts`). Coherence (ids, names derived from references, cleanup of
   orphans) is a hook, not a verb the caller must remember.
3. **Is it a domain verb every consumer of this schema could use?** → an **extension** in the
   dialecte package (`extensions/<ns>/query|transaction/<verb>.ts`).
4. **Is it schema-agnostic engine behaviour** (traversal, mutation, IO, store, a missing hook
   point)? → **core**. Typed against the generic record model, tested on the dummy test schema.
5. **Only this app needs it?** → consumer code (custom extension in the app), not a dialecte change.

Two smells: a domain rule in core; a query whose only job is to feed a transaction (let the
transaction read the definition directly).

**Standard vs custom rule** (for a dialecte that implements a standard): the engine implements what
the standard says, and that is the default. A rule an expert wants that the standard does not
require is a consumer choice (an option on the verb or a policy hook, default = the standard). A
rule that contradicts the standard stays out of the engine (consumer override).

## The workflow

1. **Orient**: read the nearest existing example of what you build (an extension in the same
   package, a hook sub-file, its test) and the package's `doc/` page for the surface. Copy shapes,
   don't invent them.
2. **Red first, vertically**: one table case with `only: true`, red for the right reason, minimum
   code, next case. See the `dialecte` skill's references/testing.md.
3. **Implement under the code rules**: [references/code-rules.md](references/code-rules.md).
   Read it before writing the first line; most review comments come from it.
4. **Gates** (below), then docs + CHANGELOG if the surface changed.
5. **Independent review**: have a fresh reviewer (a sub-agent with only the spec, the diff and
   these rules, or a human) read the diff against the previous version before hand-over. Self-review
   re-reads your own intent and misses weakened assertions and unusable types.
6. **Hand over** with a commit-by-lots script: [references/landing-changes.md](references/landing-changes.md).
   The agent never commits or pushes.

## Definition of Done - every change, in the changed package

1. `npm run check` - type-checks sources AND tests, lint, format. Never a bare `tsc --noEmit`
   (`tsconfig.json` is a solution file and checks nothing).
2. `npx oxfmt <changed files>`.
3. `npm run build` - runs the type-check in parallel and emits declarations (vite-plugin-dts),
   which catches union-assignability errors the editor misses.
4. `npx vitest run` - full suite green (`npm run test` is watch mode in some packages; create uses
   `npm run test:ts` + `test:py`). `npx vitest run <path>` while iterating.
5. `npm run doc:build` - the VitePress docs build.

If public API or user-visible behaviour changed, it is not done until you also:

- update the `doc/` page that describes that surface (types, verbs, contracts),
- add a line under `## UNRELEASED` in the package's `CHANGELOG.md`, written for the user, and
- update the package's `skills/` when the change touches what a skill describes (API, hooks,
  extensions, scripts, layout, rules): `npm run skills:generate` refreshes the generated tables,
  `npm run skills:check` (run it with the other gates) fails on any name, path or script a skill cites
  that no longer exists. Both scripts call `@dialecte/cli` 0.2.0 or later; with an older cli in the
  package, run `npx @dialecte/cli@latest skills generate` / `npx @dialecte/cli@latest skills check`.

Type performance: `npm run type-bench:check` compares type instantiations with
`benchmarks/types/baseline.json` (one per version folder in a dialecte package:
`benchmarks/types/<version>/baseline.json`; 5 % gate). A breach is a **think point**, not a wall: measure
and explain the growth; if it is legitimate, re-baseline with `npm run type-bench` in its own lot.
Never hand-edit `baseline.json`, never twist code to dodge the gate.

Run slow gates (create's `npm run proof`, corpora, mutation testing) once per lot before hand-over,
not after every fix. Fast targeted runs while iterating.

## Cross-package changes

A dialecte package depends on a **published** core version (an installed copy, not a symlink). A
core change is invisible to the package until you: build core → put its build where the package
resolves it (`npm install ../core` in the package, a symlink
`<package>/node_modules/@dialecte/core -> ../../../core`, or a copied `dist/`) → delete the package's
`node_modules/.vite` (vitest pre-bundles deps and keeps the old core). Before committing, the
package must depend on a released core version again; never commit the link. Release order: core
first, then the packages that pin it, each with its own bump lot.

## Verification traps (false greens)

Read [references/traps.md](references/traps.md) before trusting any gate output. The short list:
solution tsconfig checks nothing; tests have their own tsconfig; stale `.vite` cache after a core
swap; output-compacting shell wrappers can turn a failing gate into "ok" (run verdict gates raw and
read the counts); a doc build can rewrite a generated data file (restore it before the hand-over
script is written); before `@dialecte/cli` 0.2.0, `dialecte bench --help` runs the
bench and writes the baseline; a test that passes on its first run may be green by accident.

## Skills ship with the code

Each package carries the skills that describe it in `skills/<name>/` (published in its npm tarball):
core has `dialecte`, `dialecte-contributing` and `dialecte-lot`, create `dialecte-create`, and every dialecte
package its own `dialecte-<id>` with the knowledge of its schema. A skill changes in the same PR as the code it describes - never
in another repository afterwards. `@dialecte/cli` maintains them:

| Command                    | Does                                                                                                                                                                                      |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dialecte skills sync`     | installs the skills of the app's dependencies into `.claude/skills` + `.agents/skills` (`--agent claude,copilot,agents`, `--copy`); `--from <workspace>` takes them from local checkouts  |
| `dialecte skills generate` | rewrites the `<!-- dialecte-skills:generated ... -->` blocks (verb map, method index, hook files) from the source                                                                         |
| `dialecte skills check`    | frontmatter, links, and every API / path / npm script a page cites must exist; generated blocks must be fresh; `--workspace <dir>` also verifies pages that describe several repositories |

Write claims so the check can verify them: API as `query.<method>` / `tx.<ns>.<verb>`, paths
relative to a package, scripts as `npm run <script>`. A deliberate mention of something outside the package goes in
`<!-- dialecte-skills ignore: token -->`.

## Performance work

Measure, don't guess: [references/perf.md](references/perf.md) (perf helper, node bench harness,
browser timeline, CPU profile). Classic regressions to avoid in review: per-element ancestor walks,
per-element queries without a cache, re-reading the same records in several passes, store reads
during import (import is in-memory two-pass by design, see the hooks rules in the `dialecte` skill).

## Never

- Edit a `*.generated.ts` file (regenerate with `dialecte-create`).
- Add a domain rule to core because it was convenient.
- Restate a registry or the definition by hand (see code-rules).
- Commit, push, or touch a repo's git index while a hand-over script may be running.
- Leave a known improvement as a "note for later" without doing it or explaining why you cannot.

## Retro gate - before you hand over

List in your hand-over every place where this skill was wrong, missing or misleading for the task,
and every correction the user made that a skill should have prevented. Then:

- **Inside a dialecte repository**: draft each skill edit as before/after and show it to the user; an
  approved edit goes in the same change (skills ship with the package that owns the code), through
  skill-creator - the eval case first, failing on the current text, as `dialecte-lot` describes - then
  `npm run skills:generate` and `npm run skills:check`.
- **In an app**: draft an issue for the package that ships the skill - the statement that was wrong
  or missing, the evidence (file, behaviour), the wording you propose - and show it to the user.
  Post it only with their approval.
- Nothing to report: write "skill retro: nothing".
